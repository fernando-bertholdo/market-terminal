01 · O Problema

Por que projetos tech derrapam silenciosamente

Três dores que aparecem em quase todo projeto sem estrutura — e que comprometem prazos, custo e qualidade antes da primeira linha de código.

Contexto perdido

Cada nova sessão recomeça do zero. Decisões viram folclore oral. Onboarding de novos membros leva semanas até a primeira contribuição confiável.

Sintoma: "alguém lembra por que escolhemos X?"

Planning ad-hoc

Planos nascem em chats, viram tickets e desaparecem. Risco não é registrado, critério de aceite é informal, decisões não têm lock — cada PR reabre debates.

Sintoma: "achei que tínhamos decidido isso"

Drift entre componentes

Docs, código e roadmap divergem com o tempo. Isonomia documental quebra. Equipe vai vivendo de heurística, não de fonte de verdade.

Sintoma: "o doc diz uma coisa, o código outra"
↓

O template resolve isso com um processo declarado, skills automatizadas e gates obrigatórios — não com mais documentação para ler.

02 · Visão End-to-End

A jornada do produto, em uma página

Do kickoff inicial à entrega contínua, cada fase tem skill responsável, artefato produzido e gate de qualidade. O ciclo se repete por milestone.

  1. 1

    Kickoff

    Substituição de placeholders, definição de stakeholders, escopo macro.

    kickoff-prompt validate-kickoff
    → documents/core/Projeto.md
  2. 2

    Design Sprint

    Exploração estratégica: visão, restrições, métricas, riscos. Tier 1 obrigatório.

    design-sprint
    → documents/strategy/*
  3. 3

    TAP

    Termo de Abertura gerado a partir de materiais brutos (PDFs, transcrições).

    generate-tap
    → documents/archive/TAP.md
  4. 4

    Roadmap & TODO

    Fases, milestones, DoR/DoD declarados. Single source of truth.

    update-docs
    → documents/core/Roadmap.md
  5. 5 o motor

    Milestone Loop ⟳

    Ciclo iterativo: init → DoR → planning → execução → DoD → reconcile → archive.

    enhanced-planning +7 skills
    → .planning/<initiative>/
  6. 6

    Release

    Entregas validadas, reconciliação documental, archive da initiative.

    reconcile-initiative archive-initiative
    → .planning/_archive/

As fases 1–4 acontecem uma vez (kickoff do projeto). O milestone loop (5) se repete tantas vezes quanto necessário até a release (6). É no loop que mora o enhanced-planning.

03 · O Coração

O loop do enhanced-planning

Cada milestone (ou detour) passa por este ciclo. Skills se encadeiam, gates bloqueiam progresso sem evidência, e o trabalho permanece reproduzível entre sessões.

flowchart TB A([1 · init-milestone]):::stepInit --> B{2 · validate-dor} B -->|DoR PASS| C([3 · enhanced-planning]):::stepHero B -->|DoR FAIL| Z[/volta para dependências/]:::stepBlock C --> D([4 · writing-plans]):::step D --> E([5 · execução dos slices]):::step E --> F{6 · validate-dod} F -->|DoD PASS| G([7 · reconcile-initiative]):::step F -->|DoD FAIL| E G --> H([8 · archive-initiative]):::step H -.->|próxima initiative| A classDef step fill:#1a2238,stroke:#475569,color:#e5e7eb,stroke-width:1.5px classDef stepInit fill:#1e293b,stroke:#60a5fa,color:#e5e7eb,stroke-width:2px classDef stepHero fill:#3b1d6b,stroke:#a78bfa,color:#fff,stroke-width:2.5px classDef stepBlock fill:#3f1d1d,stroke:#f87171,color:#fecaca,stroke-width:1.5px
  1. init-milestone Cria a infraestrutura: .planning/<initiative>/ com CONTEXT.md, handoff/, plans/.
  2. validate-dor gate Bloqueia se Definition of Ready não estiver 100% completo. Sem DoR, não começa.
  3. enhanced-planning Injeta os 13 guardrails estruturais no plano antes de uma linha sequer ser escrita.
  4. writing-plans Preenche o plano usando os guardrails como esqueleto obrigatório.
  5. execução dos slices Implementação em chunks ≤100 linhas, com commits atômicos e checkpoints humanos.
  6. validate-dod gate Roda verify: steps, gera relatório PASS/FAIL. Não passa sem evidência.
  7. reconcile-initiative Reconcilia decisões e learnings em Projeto.md, Roadmap.md, TODO.md.
  8. archive-initiative Move para _archive/ com INDEX.md. Próxima initiative herda contexto limpo.
04 · Os Fluxos Vivos

Quem fala com quem, em que ordem

Os diagramas anteriores mostraram estados. Aqui você vê atores e tempo. Quatro fluxos que constituem o coração operacional do template — alterne entre eles para comparar.

Por que importa

A janela de contexto da LLM é finita. Sem protocolo de handoff, cada sessão recomeça do zero — decisões viram folclore oral.

  • O CONTEXT.md é o registro vivo do milestone (decisões, próximo passo, blockers).
  • fresh-context dispara automaticamente acima de ~150k tokens.
  • Snapshot em handoff/ permite auditar a evolução.

Por que importa

Tarefas com 3+ subtarefas independentes ganham 2-3× em paralelismo. Lead delega; teammates executam; Lead consolida.

  • Só o Lead commita — teammates não tocam git, docs core ou TODO.md.
  • Haiku para pesquisa, Sonnet para implementação, Opus para coordenação.
  • Delegate Mode (Shift+Tab) restringe Lead a coordenar — evita que vire mais um implementador.

Por que importa

Gates de qualidade dos dois lados: nada começa sem DoR, nada termina sem DoD. Cada slice é independente e bisect-friendly.

  • DoR bloqueia — dependências não satisfeitas viram tarefas, não código.
  • Loop por slice — máximo 100 linhas por commit, CONTEXT.md atualizado a cada um.
  • DoD valida com evidência — não é checkbox, é verify: step com saída.
validate-dor validate-dod organize-commits reconcile-initiative

Comparativo: Handoff é tempo entre sessões. Agent team é paralelismo dentro de uma sessão. Onboarding mostra como a consultoria adota o template. PR lifecycle mostra o que acontece em cada milestone.

05 · Anatomia do Motor

Os 13 guardrails que tornam um plano completo

O enhanced-planning não escreve o plano — ele garante que nenhuma seção crítica falte. Cada guardrail responde a uma falha recorrente em planos ad-hoc.

01

Contexto

Problema + resultado esperado declarados antes de qualquer implementação.

02

Implementação por PRs

Slices, arquivos tocados e critérios de aceite mapeados por PR.

03

Checkpoints humanos

Mínimo 6 pontos de confirmação: design, mid-point, final, +1 por PR.

04

Guardrails nomeados G-*

Selecionados do catálogo, com verificação por slice.

05

Risk registry

Severidade, mitigação, owner e status para cada risco identificado.

06

Tabela de progresso

Vazia, pronta para preencher. Estado público do milestone em tempo real.

07

Isonomia documental

Tabela de verificação cruzada entre código, docs e planos.

08

Revisão Codex

Por PR + meta-avaliação via /codex:rescue --effort xhigh.

09

Decision locks

Decisões trancadas com tracking. Não reabre sem evidência nova.

10

Conclusão de PR

Checkboxes obrigatórios + atualização de CONTEXT.md por PR.

11

Protocolo multi-sessão

4 regras de continuidade. CONTEXT.md atualizado a cada pause point.

12

Sequência de commits

Tabela ordenada com PR + tipo + scope. Bisect-friendly por construção.

13

Verificação final

10+ itens obrigatórios. Inclui CONTEXT.md, isonomia, evidências.

✓

Antes de o plano ser aceito, enhanced-planning executa 10 checks de completude. Se algo falta, o plano volta para o board — não vira código.

06 · Continuidade

O trabalho sobrevive ao fim da sessão

Cada milestone tem um CONTEXT.md vivo. Quando uma sessão chega ao limite de tokens ou termina o expediente, o estado é congelado e a próxima retoma sem perda.

⌘

Sessão ativa

Trabalho acontece. CONTEXT.md da initiative é atualizado continuamente — estado, decisões, próximo passo.

❄

Pause point

fresh-context congela um snapshot em handoff/<id>-CONTEXT.md quando a sessão excede ~150k tokens.

↻

Nova sessão

generate-session-prompt monta o prompt de retomada a partir do CONTEXT vivo + último handoff. Zero contexto perdido.

Por que importa

  • Janela de contexto da LLM é finita. Trabalho longo precisa de handoff explícito.
  • Trocas de agente são reais. Codex → Claude → outro humano. Todos precisam do mesmo briefing.
  • Decisões perdidas custam caro. O CONTEXT.md é o registro vivo do "porquê".
.planning/<initiative>/CONTEXT.md living document · atualizado a cada checkpoint
07 · Mapa do Território

Onde cada coisa vive

O template tem três grandes territórios — regras, fonte de verdade e trabalho. Cada artefato tem casa, lifecycle e owner. Sem ambiguidade.

⚙

Regras & Skills

O "como" do projeto. Não muda com features.

  • .claude/CLAUDE.mdregras sempre-ativas
  • .claude/rules/regras path-targeted
  • .claude/skills/workflows automatizados
  • .claude/hooks/quality gates automáticos
★

Fonte de Verdade

Decisões de negócio e arquitetura. Projeto.md prevalece.

  • documents/core/Projeto.mdliving doc · single source of truth
  • documents/core/Roadmap.mdfases, milestones, DoR/DoD
  • documents/core/TODO.mdtarefas granulares
  • documents/strategy/visão, métricas, riscos (Tier 1)
  • documents/technical/arquitetura, integrações
  • documents/archive/TAP, transcrições, histórico
⟳

Trabalho em Andamento

Initiatives ativas. Lifecycle: ativo → concluído → arquivado.

  • .planning/<initiative>/CONTEXT.md + plans + handoff
  • .planning/patches/correções ≤2 sessões
  • .planning/scratch/context dumps efêmeros
  • .planning/audit-reports/reconciliation + drift
  • .planning/_archive/initiatives concluídas + INDEX.md

Regras de ouro

1

Projeto.md prevalece. Conflito entre docs? Vale o que está em core/.

2

Planos não são doc. Vivem em .planning/ e morrem no archive. Código + commits são a verdade pós-implementação.

3

Toda decisão deve refletir em Projeto.md. Strategy/technical são suplementares, sempre com backlink.

08 · Para a Consultoria

Plug & Play em 5 passos

Adotar o template em um cliente novo. Da clonagem do repo ao primeiro milestone rodando no loop completo — tipicamente em menos de uma semana.

  1. 01

    Clone do template

    Fork ou clone direto. O template já vem com .claude/, .codex/, .agents/ sincronizados e estrutura de docs completa.

    git clone <tech-product-template> meu-cliente
cd meu-cliente
  2. 02

    Kickoff guiado

    Roda o kickoff-prompt com o cliente. Substitui placeholders (Market Terminal, stakeholders, stack) em todos os arquivos automaticamente.

    /kickoff-prompt
  3. 03

    Validação do kickoff

    validate-kickoff detecta placeholders esquecidos e inconsistências entre arquivos. Gate bloqueador — não avança sem 100%.

    /validate-kickoff
  4. 04

    Estratégia & TAP

    Se cliente tem materiais brutos, generate-tap os transforma em TAP estruturado. Em paralelo, design-sprint destila visão, métricas e riscos para documents/strategy/.

    /generate-tap
/design-sprint
  5. 05

    Primeiro milestone no loop

    Define Roadmap.md, escolhe primeiro milestone, entra no loop completo. A partir daqui, é o enhanced-planning dirigindo.

    /init-milestone M1.1
/validate-dor M1.1
/enhanced-planning M1.1
